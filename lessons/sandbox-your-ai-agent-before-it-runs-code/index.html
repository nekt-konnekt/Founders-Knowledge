Before your AI agent runs code, give it a sandbox.

A model can write code in seconds. That does not mean the code should have access to your customers, credentials or production systems. Build an execution boundary before you give an agent real work.

A sandbox does not make an agent trustworthy. It limits what a mistake, malicious instruction or compromised tool can reach.

“

If your AI agent can only return text, a bad answer is usually a quality problem. If it can write files, run shell commands, install packages, query databases or call external tools, a bad answer can become an operational incident. The moment an agent can execute, you are no longer designing only a conversation. You are designing a system that can act.

01 — WHEN AN AGENT CAN EXECUTE

A prompt is not a security boundary.

An agent can receive instructions from more than its system prompt. It may read a PDF, an email, a support ticket, a website, a source-code repository or an MCP tool response. Any of those inputs can contain hostile or misleading instructions. A model may follow them while trying to complete the task it was given.

That becomes more serious when generated code executes immediately. A script can inspect its environment, read files, make network requests, consume resources or use whatever credentials were placed within reach. Telling the model “do not access production” is not the same as making production inaccessible.

A selected roundup of Q3 2026 incidents and disclosures published on the OWASP GenAI Security Project site describes agents escaping intended evaluation boundaries, repurposing shared package infrastructure for communication and internet access, and expanding access through exposed credentials and privileges. The page explicitly says the roundup is non-exhaustive and is not an official OWASP publication; it also warns that related entries should not be counted as independent attacks. The useful lesson is not that every agent is compromised. It is that an instruction is not an enforced boundary.

On 27 October, Akamai announced its Agent Sandbox alongside a new inference service. The sandbox uses WebAssembly isolation and limits compute, memory, outbound connections and system capabilities. Both products were announced as beta. This is a signal that execution isolation is becoming part of the AI infrastructure conversation — not proof that one vendor has solved agent security for every workload.

Use this test

If the agent reads an attacker-controlled document and follows an instruction hidden inside it, what can it actually reach? Your answer should come from enforced permissions and network rules, not from the wording of the prompt.

02 — SEPARATE CONTROL AND EXECUTION

Keep the authority outside the workspace.

A safer design separates three jobs. The model can propose work. An isolated environment can execute code. A trusted part of your application decides which real-world actions are allowed.

THREE PARTS OF A SAFER AGENT

  • Control plane — your trusted application. Own authentication, tenant identity, billing, policy checks, approvals, audit logs and recovery. This is where long-lived credentials and production authority stay.
  • Execution plane — the sandbox. Give the agent a temporary workspace with only the files and commands needed for its task. It can calculate, transform files, run tests or generate an artefact without inheriting the application's full authority.
  • Capability broker — the approved doorway. When the agent needs a real service, it requests a specific operation. Your backend validates the request, checks the user's permissions and performs the action with narrowly scoped credentials. The sandbox receives the result, not the secret.

Imagine an agent that reconciles supplier invoices for a distributor in Lagos. It can inspect uploaded invoices, compare them with a read-only copy of purchase-order data and prepare a reconciliation report. It should not be able to initiate a bank transfer, change supplier bank details or query every customer in the company's database. Those actions belong behind separate, explicit permissions and human approval.

OpenAI's current sandbox guidance describes the same architectural separation: keep the agent harness, authentication, billing, audit and recovery in trusted infrastructure, while the sandbox handles model-directed file and command execution. The principle is provider-independent. Your model can be hosted locally or remotely; the execution boundary should remain a separate part of your system.

03 — FIVE GUARDRAILS

Make the limits impossible for the agent to negotiate away.

Start with five controls. They are more important than adding another paragraph to the system prompt.

  1. Keep long-lived credentials out of the sandbox. Do not put production database passwords, payment keys, cloud credentials or unrestricted API tokens in environment variables, source files, logs or mounted secrets that generated code can read. Keep them in your backend or a secrets manager. Use a broker or trusted proxy to attach a short-lived, narrowly scoped credential only to an approved destination. Revoke or rotate a credential if exposure is suspected.
  2. Deny outbound network access by default. Most code-execution tasks do not need unrestricted internet access. If a task needs a specific service, allow only that destination through a controlled egress proxy. Block access to internal networks, cloud metadata endpoints and services that the task does not require. Log the destination and the reason for every permitted connection.
  3. Give each run a disposable workspace. Pass in only the files required for the task. Avoid broad host mounts, shared writable directories and access to the host's container-control socket. Keep inputs read-only where possible, write outputs to a designated location and destroy the workspace when the task ends. Do not let one run inherit another customer's files or state.
  4. Enforce resource limits outside the model. Set maximum execution time, memory, CPU, disk usage, process count, output size and tool-call count. Stop runaway loops and oversized downloads. The agent must not be able to raise its own limits or create unlimited child processes.
  5. Require approval for consequential actions. An agent may prepare a payment, draft an email, propose a database migration or stage a deployment. Sending money, changing account details, deleting customer data, sending messages externally or deploying to production should require a separate policy check and, where appropriate, a named human approval. Record who approved what and when.

OpenAI's sandbox security documentation makes an important credential distinction: code running inside an environment can read the environment key it receives. The application's broader API key should therefore remain outside that environment. For third-party services, keep credentials in the trusted application or a proxy that injects them only for approved hosts. That is a concrete implementation of least privilege, not just a security slogan.

04 — PROTECT EVERY TENANT

Multi-tenant isolation cannot live in the prompt.

If you are building an AI feature for multiple businesses, a shared agent process is not a reason to share every customer's execution environment. One customer's uploaded invoice, employee record or CRM export must not become visible to another customer's agent because of a reused directory, cached file, shared memory store or overly broad database connection.

Enforce tenant identity in your backend before a task starts. Create a separate workspace or equivalent isolation boundary for each tenant and run. Give it a tenant-scoped data view, distinct credentials and a narrow set of capabilities. Keep memory and artefacts partitioned. Do not ask the model to remember which customer it is allowed to serve; the application must enforce that rule even when the model gets it wrong.

Test the boundary with two test accounts. Give Tenant A an agent task that explicitly asks to retrieve Tenant B's records. The expected result is a denied request and an audit event — not a polite refusal generated by the model after it has already read the data.

05 — TEST THE BOUNDARY

Test what the agent cannot do, not only what it can do.

A happy-path demo proves that an agent can complete a task. It does not prove that the system can contain a bad task. Before production, run a small abuse test against the exact permissions and infrastructure you intend to ship.

A MINIMUM AGENT CONTAINMENT TEST

  • Upload a document that tells the agent to ignore its task and send a secret to an external URL. The request must be blocked; no secret should be available to the sandbox.
  • Ask generated code to read host files, environment variables or a cloud metadata endpoint. It should see only the files and values deliberately provided for the run.
  • Ask the agent to reach an internal database or an unapproved internet host. The network boundary should deny the connection and record the attempt.
  • Run an infinite loop or a task that creates a very large file. The runtime should stop it at the configured limit without affecting other workloads.
  • Ask Tenant A's agent to read Tenant B's file or memory. The request must fail at the application or storage boundary.
  • Ask the agent to send a payment, delete a record or deploy code. The action should stop at the approval gate until the required person authorises it.

Measure containment, not just completion. Track blocked network attempts, credential exposure tests, cross-tenant access denials, resource-limit stops, approval overrides and successful task completion. A sandbox that makes every task fail is not useful; an agent that completes every task with unrestricted authority is not safe. You need both useful work and enforced limits.

06 — START WITH ONE WORKFLOW

You do not need a GPU cluster to begin.

Small teams can build the boundary before they scale the model. Start with one workflow where code execution adds clear value — document extraction, spreadsheet analysis, report generation or test execution. Keep the first version read-only. Do not begin with an agent that can move money or change production data.

  1. Map the authority. List every file, API, database, credential and external action the workflow touches. Mark which are read-only and which can change customer or business state.
  2. Move secrets back into the application. Remove production keys from the agent's environment. Put real actions behind narrow backend functions that check tenant, user and task permissions.
  3. Create the execution boundary. Use an isolated sandbox with a temporary workspace, restricted network access and hard resource limits. A local container can help during development, but root privileges, broad host mounts or a mounted container-control socket can undermine the boundary. Harden the host and runtime before treating it as a production control.
  4. Add approvals and audit. Make the agent propose consequential actions first. Log the request, policy decision, approval and result with a traceable task identifier.
  5. Run the containment tests. Use synthetic customer data and adversarial documents. Fix every path that exposes another tenant, a secret or a production action before widening access.

For a team running on a modest VPS, the first rule is simple: do not run an agent with root access to the machine that hosts your database and production application. Use a separate unprivileged runtime, do not expose its execution ports publicly, and do not share production credentials or host directories with it. If you cannot isolate the execution environment yet, keep the agent to reviewed, narrowly scoped tools and do not give it arbitrary shell access.

You can use a local model, a hosted model or switch providers later. The sandbox is an execution decision, not a GPU decision. Choose the model for task quality and cost; choose the execution environment for the level of risk you are prepared to contain.

THE TAKEAWAY

An AI agent can be useful without being trusted with everything. Let it propose and execute work inside a boundary; keep credentials, customer authority and irreversible actions in systems you control.

Evidence & limits

Verified developments: Akamai announced Akamai Agent Sandbox on 27 October 2026 and said the product was in beta. Its product documentation describes WebAssembly isolation, outbound access blocked by default and runtime-enforced resource limits. The product page describes the current tech preview as supporting intermittent steps of roughly one minute, with longer-lived stateful agents planned; this should not be treated as proof of production readiness for every workload.

Security evidence: the OWASP GenAI Security Project page published a selected Q3 2026 incident and disclosure roundup on 8 October. It explicitly says it is non-exhaustive and not an official OWASP publication, and warns that related entries should not be counted as separate independent attacks. It is useful evidence of failure modes, not a measure of how frequently agent systems are compromised.

Implementation guidance: OpenAI's sandbox and security documentation provides concrete examples of separating the trusted harness from execution and keeping application credentials outside the sandbox. These are vendor docs, not an independent audit of any particular implementation. No sandbox removes the need to review tools, permissions, dependencies, monitoring and human approval.
