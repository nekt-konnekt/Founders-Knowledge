Your App Should Not Stop Working When the Network Does

Design offline-first products so customers can keep working, even when connectivity disappears. A practical guide to local data, synchronization and safe recovery.

“

A teacher marks attendance for 32 students. The connection drops just before the records are saved. The application displays an error. The teacher tries again, but now nobody knows which records reached the server. The problem is not simply that the internet went away. The product made the customer's work depend on the internet being available at exactly the right moment.

01 — OFFLINE-FIRST IS NOT CACHING

A page that opens offline is not necessarily a product that works offline.

Caching helps a browser retrieve resources it downloaded earlier. A service worker can intercept network requests and return cached assets or a fallback page. That is useful, but it does not automatically save a customer's form, record or transaction.

Imagine a sales representative opens a cached customer page, fills in an order and presses Save. The page is available. The server is not. If the application only sends the order to a remote API, the work still fails.

An offline-first product is designed so its critical jobs can continue without a live connection. It has a local data source, a deliberate way to store changes, and a synchronization process that sends those changes when the network returns. Google's Android guidance describes offline-first applications as those that can perform all or a critical subset of core functionality without internet access.

!
Do not confuse an offline screen with an offline workflow.

The real test is whether the customer can complete and safely retain the work they came to do.

02 — CLASSIFY EACH OPERATION

Not every action should be allowed offline.

Start with the customer's jobs, not with a service worker or a database choice. For each operation, decide what should happen when connectivity disappears.

THREE OFFLINE POLICIES

Local-first: Save locally and let the customer continue. Use this for drafts, attendance records or notes when the business rules allow later synchronization.

Queued: Store the operation for later delivery. Use this for work such as analytics or notifications that does not need an immediate result.

Online-only: Require a live server response. Use this for actions that need current authority or external confirmation, such as initiating a bank transfer or changing sensitive account permissions.

Google's offline-first guidance describes these different write strategies. The right choice depends on the consequence of delaying an operation and the risk of accepting it without server-side checks.

These are starting points, not universal rules. For example, an order draft may be local-first while final price, stock availability and payment confirmation still require the server.

03 — USE A LOCAL SOURCE OF TRUTH

Let the interface read from local data, not wait for every API call.

A useful architecture separates the user interface from the way data is stored and retrieved. A repository coordinates a local database and a remote API. The interface reads from local storage, while the repository refreshes or synchronizes remote changes.

For a web application, IndexedDB can store structured records in the browser. A service worker can manage application resources and network requests. These have different jobs: IndexedDB stores application data; the service worker helps manage how the application responds to network conditions.

The local database is the immediate source for the device's view. The remote server remains the shared system of record. That distinction helps the application respond quickly without pretending that every local change has already been accepted by the server.

04 — SAVE BEFORE SYNCING

Make the local save and the server request two separate events.

For an operation that is allowed offline, the application should validate the input, generate a stable operation ID, save the record locally, add it to a persistent outbox and update the interface. It can then attempt to deliver the operation to the server.

A simplified attendance record might look like this:

{
  "operation_id": "op_8f32a1",
  "student_id": "student_104",
  "class_id": "class_12",
  "attendance_date": "2026-11-02",
  "status": "present",
  "recorded_by": "teacher_09",
  "created_at": "2026-11-02T08:15:00Z",
  "sync_status": "pending"
}

The operation ID should remain the same across retries. The server should use it to recognize a repeated submission and avoid creating a second attendance event when the first response was lost.

This is the purpose of idempotency: repeating the same operation should not create a second business effect. A network timeout does not tell the client whether the server received the request. Stable identifiers and server-side duplicate protection make retries safer.

↻
Keep the outbox persistent.

Do not store pending operations only in application memory. They should survive a closed tab, an application restart and a device reboot.

Retry temporary failures with increasing delays, often called exponential backoff. Do not retry every error forever. A network interruption may be temporary; an expired session or invalid record needs a different response. Preserve the pending operation and tell the user what needs attention.

05 — HANDLE CONFLICTS DELIBERATELY

Two devices can make valid changes while disconnected.

A teacher records attendance on one device. An administrator corrects the same record on another. Both devices are offline. When they reconnect, the application must decide how to reconcile the changes.

One simple rule is last-write-wins: accept the update with the latest timestamp. That may be acceptable for a low-risk preference, but it can be dangerous for business records. Device clocks can be wrong, and a later edit can erase an important earlier change.

Choose conflict rules based on the meaning of the data:

  • Personal notes: a latest-version rule may be acceptable if the product preserves edit history.
  • Attendance: preserve who changed a record, when and why; corrections may need an audit trail.
  • Inventory: record stock movements rather than allowing disconnected devices to overwrite a shared total.
  • Money: do not reconcile financial transactions by choosing the latest device timestamp. Use authoritative transaction processing and reconciliation.

For important records, a conflict should be visible and recoverable. It is better to ask an authorised person to resolve a genuine conflict than to silently discard a valid change.

06 — DO NOT DEPEND ON ONE BROWSER API

Background sync is useful, but it cannot be your only delivery plan.

The Background Synchronization API lets a service worker defer some work until a browser detects connectivity. It can improve the experience, but browser support is limited. Do not make your only synchronization path depend on it.

Also attempt synchronization when the application opens, when the user returns to it and when connectivity is restored. Keep a visible retry option for failed operations. The queue itself must remain durable even if the browser never runs a background task.

For native Android applications, WorkManager is a common option for persistent, deferrable background work. Choose platform tools based on the devices and browsers your customers actually use, and test the complete workflow on those platforms.

07 — SHOW AN HONEST STATUS

Do not tell customers a change succeeded when it has only been saved locally.

Offline-first changes the interface as well as the architecture. A single green success message is not enough. The customer needs to know whether a record is stored on the device, waiting to synchronize, confirmed by the server or blocked by a problem.

FOUR STATES TO MAKE VISIBLE

Saved on this device: the local database has stored the work.

Waiting to sync: the operation is queued for delivery.

Synchronized: the server has acknowledged the operation.

Needs attention: the operation needs a retry, sign-in or human decision.

Show how many operations are pending and when the last successful synchronization occurred. If something fails, explain what happened and what the customer can do. Do not hide pending work behind a generic error message.

08 — TEST THE FAILURE PATHS

Airplane mode is only the first test.

Test the workflow under the conditions it claims to support. Include slow connections, dropped requests, application restarts, expired sessions, duplicate submissions and two devices changing the same record.

PUT IT TO WORK

Run this offline-readiness test.

  1. Open the application offline. Previously loaded critical information should still be available.
  2. Create a record offline. It should be saved locally and clearly marked as pending.
  3. Close and reopen the application. Pending records should still exist.
  4. Restore connectivity. Pending operations should begin synchronizing.
  5. Drop the connection during synchronization. Unconfirmed operations should remain pending.
  6. Submit the same operation twice. The server should not create duplicate business records.
  7. Expire the user's session. Protected operations should not be silently accepted or retried forever.
  8. Edit the same record on two devices. The conflict should follow a documented rule.
  9. Fill local storage. The application should explain the problem and must not claim unsaved work is safe.
! Reality check

Offline support increases responsibility for data stored on a device. Consider device access, local encryption where appropriate, sign-out behaviour, data retention and what happens when a device is lost. Offline access should not bypass your product's security model.

WHAT TO BUILD FIRST

Start with one critical customer workflow.

You do not need a sophisticated distributed system for your first release. Pick one workflow—recording attendance, saving a field-sales order draft or capturing an inventory movement—and make that workflow reliable.

First, store the records needed for the task locally. Then save new work locally, create a persistent outbox and synchronize when possible. Add duplicate protection and clear status messages. Only then expand to multi-device conflict handling and more complex workflows.

Measure whether the customer can complete the job, how many operations remain pending, how long synchronization takes and how often conflicts need intervention. Those measures tell you more about the quality of the offline experience than whether the page happens to open in airplane mode.

THE TAKEAWAY

Build around the customer's ability to finish the job—not around the assumption that the internet will always cooperate. Some operations must stay online. Others can safely wait. Know the difference, save the work locally, synchronize it deliberately and tell the customer what has actually happened.
