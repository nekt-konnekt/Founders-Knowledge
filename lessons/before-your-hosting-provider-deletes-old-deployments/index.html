A deployment is not just a historical entry. It can be a recovery point. Before old deployments are removed, decide which recovery options your product actually needs.

01 — WHAT VERCEL ANNOUNCED

The date is real. Your team’s exact billing start still needs checking.

On 9 October 2026, Vercel announced that Deployment Storage and Functions Storage billing would begin for existing Pro teams at $0.10 per GB-month for each storage category. Vercel says to check the email sent to your team for its specific billing start date.

The same announcement says the deployment retention window changes to 30 days, with deployments older than 30 days scheduled to begin deletion on 23 October 2026, unless you opt out through retention settings before then. Settings already at 30 days or shorter are unchanged.

This is the announced policy—not proof that your own account is on Pro, that billing has started for your team, or that a particular deployment will be deleted. Confirm those details in the Vercel team and project settings.

Important distinction

Deleted deployments cannot be used for rollback. Do not assume that keeping your source code alone preserves every deployment-specific recovery option.

02 — CHECK YOUR TEAM SETTINGS

Verify the policy before changing anything.

Open the correct Vercel team, then inspect the project and team-level deployment retention settings. Do not rely on memory or on a setting from a different team.

01Confirm the plan

Check whether the relevant team is on Pro and read Vercel’s email for the billing start date that applies to that team.

02Review each retention category

Check Production, Pre-Production, Canceled, and Errored deployments. The retention policy may differ by category.

03Check storage usage

Open the Usage page and review Deployment Storage and Functions Storage per project. Record the current usage before optimizing.

If you need deployment history beyond 30 days, review the available retention options and opt-out process in your own settings before the deadline. A longer retention period can preserve more history, but it can also increase storage use and cost.

03 — PROTECT ROLLBACK OPTIONS

Identify the deployments you would actually want back.

Do not preserve every old deployment blindly. Start with the releases that would matter during an incident, then verify what recovery depends on.

Mark these before you make retention changes
  • The current production deployment and the last known-good release.
  • Any release tied to a high-risk change, such as authentication, payments, or a major routing change.
  • Deployments you need for an active investigation, customer incident, or comparison.
  • The commit SHA, branch, and release notes for each important deployment.
  • Any environment-specific configuration or build detail needed to reproduce the release—without copying secrets into notes or public files.

Confirm that the source repository and required build inputs are still available. Document environment-variable names, not secret values, and make sure secrets can be recovered from the proper secure store.

Remember: rolling back the frontend or server deployment does not automatically reverse a database migration, restore deleted customer data, or undo an external side effect. Database changes need their own tested recovery plan.

04 — UNDERSTAND STORAGE COST

Measure your actual usage instead of guessing.

At the announced rate, a simple illustration is 20 GB of billable storage × $0.10 = $2 per month for that storage category. This is only an example, not an estimate of your bill: actual usage, billing timing, and the storage categories shown in your account determine the real amount.

Deployment Storage and Functions Storage are separate categories in Vercel’s announcement. Check both in the Usage page rather than treating one number as the full cost.

To reduce unnecessary storage, inspect large build outputs and files that do not need to be bundled into deployments. Move suitable large assets to object storage and reduce oversized Function bundles only when it is safe for your architecture. Do not delete recovery points just to make the usage graph smaller before you have checked what depends on them.

05 — YOUR 15-MINUTE AUDIT

Complete this before the retention change.

  • Confirm the team and plan associated with the project.
  • Read the Vercel email and note the billing start date for that team.
  • Check Deployment Storage and Functions Storage on the Usage page.
  • Review retention periods for Production, Pre-Production, Canceled, and Errored deployments.
  • Identify the current production release and last known-good deployment.
  • Record the commit SHA and verify the source code and build inputs are recoverable.
  • Check whether database migrations require a separate rollback or restore procedure.
  • If you need longer deployment history, adjust retention or opt out using the controls available in your account before the deadline.
  • Test the recovery process in a safe environment and record who owns it.

Only after this check should you shorten retention or remove old deployments. A setting change is not a substitute for a tested recovery plan.

YOUR NEXT STEP

Pick one release you could safely recover to.

Write down its deployment URL or identifier, source commit, required configuration, and any database or external changes that would affect a rollback. If you cannot explain how to recover, your next task is to document and test that path.
